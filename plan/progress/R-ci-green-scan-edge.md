## Evidence and cause

The journey assertions are valid: they check the entire visible chip against
the viewport and touch controls. Inspected retained `517c56b1` manifests,
screenshots and Playwright error contexts from the main checkout. Both desktop
cases passed; all four phone cases failed:

| Case              | Step        | Failure                                                      |
| ----------------- | ----------- | ------------------------------------------------------------ |
| Titanic 390x844   | second-scan | Chip right edge 538 > viewport 390                           |
| Blue Hole 390x844 | first-scan  | Chip right edge 538 > viewport 390                           |
| Titanic 844x390   | first-scan  | Chip right 596.484375 overlaps controls starting at 588.8125 |
| Blue Hole 844x390 | first-scan  | Chip right 1077.15625 > 844; bottom 453.84375 > 390          |

`Waypoints.update()` already measures wrapped copy and searches for a placement
clear of the composed HUD. However, the shared touch rule used `display: none`
while the guidance slot showed a scan card. A mission change during scan
completion updates the next waypoint while that rule still applies. Its
measured size is zero, so the collision search clamps a point rather than the
label. The result card then reveals the full label at that invalid position,
before another rendered frame can correct it. This also explains why the
existing direct waypoint-layout tests miss this particular lifecycle transition.

Changed that one shared rule in `src/styles/hud-layout.css` to
`visibility: hidden`. The scan card and reticle retain priority, and the
existing placement code can measure the next label before it appears. No new
guidance surface, viewport exception, site branch, offset or placement machinery.
The journey and capability assertions are unchanged.

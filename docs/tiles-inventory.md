# Tile inventory

Tiles for the owner-approved Tier-2 list (`plan/DECISIONS.md`). They are generated by
`tools/fetch_all.py` (the three older tiles by `tools/fetch_tile.py`, reproduced with the
same pinned bboxes) and compressed by `tools/compress_tiles.py`. Tile id equals landmark id
in `data/landmarks.json`. Format: `docs/tile-format.md`.

Generated 2026-09-23 (UTC) from GMRT v4.5.0 (June 2026 release). Every Tier-2 landmark has
a tile. No landmark needed the ETOPO fallback, and no request failed or had to be retried.

## Compression (`tools/compress_tiles.py`)

| variant                     | Tier-2 bytes | vs f32 |
| --------------------------- | ------------ | ------ |
| `heightmap.bin` (float32)   | 29,365,336   | 100 %  |
| `heightmap.bin.gz` (gzip 9) | 18,135,646   | 61.8 % |
| `heightmap16.bin` (uint16)  | 14,682,668   | 50.0 % |
| `heightmap16.bin.gz`        | 12,191,778   | 41.5 % |

- gzip does poorly on raw float32 depths. Per-tile results range from 46 % of the original (smooth Endurance) to 80 % (rough, multibeam-rich tiles). Every `.gz` is checked by decompressing it and comparing with the original, and files are byte-reproducible because the gzip mtime is set to 0.
- `heightmap16.bin` has a maximum error of **0.038 m** (Challenger Deep, 76 mm step), far below GMRT's own vertical accuracy.
  It is optional: `TileLoader` uses it only with `new TileLoader(root, fetch, { prefer16: true })` and falls back to float32.
- **brotli** is not installed on the build machine (`which brotli` finds nothing), so no `.br` files exist yet.
  `compress_tiles.py` writes them automatically when the CLI is on PATH. For CI:
  ```bash
  sudo apt-get install -y brotli          # ubuntu-latest runners
  python3 tools/compress_tiles.py --quant16   # now also emits heightmap*.bin.br
  ```
- The loader always requests `heightmap.bin`. The `.gz`/`.br` copies are for static hosts that serve pre-compressed
  files with `Content-Encoding`, such as nginx `gzip_static`/`brotli_static`, Netlify or Cloudflare. GitHub Pages already
  gzips responses on the fly, so there they only save server CPU.

## How to re-fetch

```bash
python3 tools/fetch_all.py --dry-run            # planned bboxes, URLs, size estimates (no network)
python3 tools/fetch_all.py --dry-run --probe    # + GMRT metadata probes (cached)
python3 tools/fetch_all.py --skip-existing      # fetch only missing tiles
python3 tools/fetch_all.py --only bismarck      # one tile (repeatable / comma-separated)
python3 tools/fetch_all.py --report --coverage  # the tables above
python3 tools/compress_tiles.py --quant16       # .gz (+ .br) and heightmap16.bin
python3 tools/inspect_tile.py <id>              # stats + ASCII map (add --variant u16)
```

- Raw responses are cached in `.cache/gmrt-raw/<id>__<kind>__<sha1-of-url>.asc|json`, so re-running with the same plan makes
  no HTTP requests. Delete a cache file, or change the plan, to force a fresh download.
- Requests are sequential and at least 2 s apart (default 2.5 s). Failures are retried up to 3 times with 5/10/20 s backoff, except
  HTTP 4xx other than 408/429, which fail immediately. If every GMRT resolution fails, the tool tries ETOPO 2022 15″ via ERDDAP.
  If that fails too the landmark is reported as FAILED, the tool exits with status 1, and nothing is written.
- Planning rules live in `tools/fetch_all.py`:
  - Boxes smaller than 0.3° are expanded around the pin, with longitude widened by 1/cos(lat).
  - Boxes are capped at 1200 native cells per side (0.659°).
  - Per-landmark `OVERRIDES` pin the three older tiles, set Challenger Deep to 0.5° and give Axial at least 0.4°.
  - A resolution is accepted if it is ≤ 8 MB float32 and ≤ 1500 cells per side; otherwise the tool steps down max → high → med → low.
- Writing a tile deletes its stale derived files (`.gz`, `.br`, `heightmap16.bin*`). Re-run `compress_tiles.py` afterwards.
